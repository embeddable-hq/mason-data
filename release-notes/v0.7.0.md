# Mason v0.7.0

**The first release of Mason from its own repository, [embeddable-hq/mason-data](https://github.com/embeddable-hq/mason-data):
the same `mason` command, now with a web page, an MCP server for Claude and other agents, a demo database to try it
on, and more of Postgres answered as Postgres answers it.** A project in replication mode needs one step before
upgrading from 0.6.1 (its slot is named differently now); a project that polls needs nothing, unless a `key:` entry
rests on no valid unique index (below).

## Before you upgrade

- **`@mason-data/cli@0.6.2` on npm is an earlier build, published by mistake, and is deprecated in favour of 0.7.0.**
  Install 0.7.0 (`npm i -g @mason-data/cli@0.7.0`); a project that ran 0.6.2 upgrades as one on 0.6.1 does, without
  the slot step below, since 0.6.2 already named and recorded its slot this way.
- **A project in replication mode on 0.6.1: drop its old slot after the first start on 0.7.0.** The slot and
  publication Mason makes on your database are now named for the project AND its source, `mason_dev_<project>_<source>`
  (the source is the name of its file under `mason/sources/`), because a project will soon sync several databases,
  each with a slot of its own. The first `mason start --replication` on 0.7.0 makes the new slot and catches every
  table up from its watermark; the old slot, `mason_dev_<project>`, is not Mason's to find any more, and a slot nobody
  reads holds your database's WAL for as long as it exists. Drop it yourself, on the source database:

  ```sql
  SELECT pg_drop_replication_slot('mason_dev_<project>');
  DROP PUBLICATION IF EXISTS mason_dev_<project>;   -- only when Mason made it; one you named is yours and stays
  ```

  `mason status` names the slot the run reads. The start now records what it made, and `mason destroy`, `mason start
  --poll` and a start under a renamed sources file drop exactly that, so a rename never leaves a slot behind again.
- **A `key:` entry must name the columns of a valid unique index.** For a table with no primary key, `mason start`
  now checks the entry against the database: its columns must be NOT NULL and cover a unique index that is valid (a
  failed `CREATE UNIQUE INDEX CONCURRENTLY` leaves one that enforces nothing, and it is not read). An entry that does
  not is refused by name, with the index to name instead.
- **Going back to an earlier release afterwards takes `mason destroy`.** Once statements sort, group or compare a
  jsonb column, 0.7.0 may store that column's order (and, under a libc collation, its equality) as a hidden column of
  the copy. 0.6.2 and 0.6.1 cannot read it: their `mason status` and every change written to that table fail. To go
  back, `mason destroy`, then copy again under that release. From 0.7.0 on, a stored column of a kind a release does
  not know is dropped at its start, never fatal.

## What changes for you

- **A web page for the run: `mason ui`.** `mason start` serves one page beside the Postgres API, with the status
  `mason status` prints (the database, each table's copy and its progress, the slow and refused statements, readiness),
  the database's tables to add and remove (as `mason add` and `mason remove` do), and the users `mason user` manages:
  list them, add one and read its password once, remove one. `mason ui` prints the page's URL with the run's token and
  opens your browser; `mason start` says only `Web UI  mason ui`, so the token never lands in a log. The page is
  `mason start`'s and loopback's: `mason serve` serves no page.
- **`mason mcp`: Mason as an MCP server, for Claude Code, Claude Desktop and any MCP client.** Its tools are `tables`
  (each with its rows and how current its copy is), `describe`, `query` (Postgres's types; a refusal with what to
  write instead) and `explain`. It connects as a `mason user`, so every statement it runs is in the request log under
  `mason-mcp/<the client's name>`, and it works beside `mason start` or against a `mason serve` elsewhere:

  ```bash
  mason user add claude                                   # the URL, printed once
  claude mcp add mason --env MASON_URL="<that URL>" -- mason mcp
  ```

  For Claude Desktop, `mason mcp --help` gives the `claude_desktop_config.json` entry (node and mason by absolute path).
- **`mason init demo`: a demo database Mason hosts itself**, nothing to install. In a new folder it makes a project on
  a synthetic shop that `mason start` runs in `.mason/demo/` and changes every few seconds, so you watch the copy keep
  current. Three of its four tables are added; `mason add order_items` after the start shows a copy beginning. It is
  polled only, and `mason destroy` removes it with the copy.
- **`mason add` and `mason remove` work before `mason start`**: `mason init && mason add orders && mason start`. With
  Mason stopped the entry is checked against the database as the run checks it, and written; the copy begins (or is
  dropped) at the next start. `--json` answers the same shape either way.
- **`mason status --json` and `mason wait --json` say how each table is kept current**, as a new `kept`: `{ by: poll,
  polledAt, unsynced, pending }`, `{ by: recopy, copiedAt }` or `{ by: replication, slot, state, why, position,
  lastCommit, notRunning }`, as each command's `--help` declares.
- **In every `--json` answer, `source` is the database and a table is `table`.** `mason status --json` used to call a
  table's name `source` (`tables[].source`); it is `tables[].table` now, as `mason tables` and `mason add` already
  said, and `source` is always one object describing the database: its `name` (the sources file's), `file`, `url`,
  and, while Mason runs, its version and how changes arrive. With Mason stopped, the sources file's problem is
  `source.error` (it was a top-level `sources`). A script reading `tables[].source` or `sources` must read the new keys.
- **A table's name has at most two parts**, `schema.table` or its name alone in `public`: `mason add a.b.c` and an
  entry `a.b.c` are refused by name, the third part reserved for the source once a project syncs several databases.
- **Copying is sized by time, not by rows, and says where it is.** A chunk is read for about 12 s whatever the table's
  width (`MASON_COPY_CHUNK_SECONDS`), so a wide table no longer stalls the progress for minutes, and `mason status`
  and `mason wait` show the chunks read, the rate, and the time left.
- **`EXPLAIN` says how each copy is kept current as `mason status` does** (by logical replication, through which
  position; by polling, with the last poll; or why it is not). `mason init` with no URL and no `DATABASE_URL` says
  what to run next.
- **`mason help production` and `mason serve --help` say how to size the server**: the copy takes half the
  container's memory limit by default, how much page cache the dashboards' columns need, cores after memory, and
  which settings to decide.

## What was wrong and is now right

- **jsonb is sorted, grouped and compared by jsonb's own order and equality**, under every collation (C, ICU, libc).
  `ORDER BY` a jsonb column (a BI tool's table view sorting by any column) used to be refused, and `=`, `IS DISTINCT
  FROM`, `NULLIF`, `CASE x WHEN`, `PARTITION BY` and `= ANY` compared the text, so `'1.0'::jsonb = '1.00'::jsonb` was
  false; all are answered now, and a sort or a group read often is stored with the copy, so it is fast. `'1'::jsonb @>
  '[1]'` is false, as in Postgres. What stays refused is listed by name in docs/SQL-SUPPORT.md (`jsonb-compare`).
  Under an ICU collation, a grouped text column sorted by its output name or ordinal is in Postgres's order too.
- **`date_trunc` of a `timestamptz` in a session zone**: below a day, across a daylight-saving change, it could give
  the other offset (02:30 CEST truncated to 02:00 +01, where Postgres gives 02:00 +02), and the three-argument form
  started its centuries in year 0. It is also several times faster in UTC.
- **A LEFT JOIN of a list's rows `ON TRUE`** (`jsonb_each`, `json_array_elements`, `unnest`, …) under a `LIMIT`, or
  under a row count the client sets on the wire (JDBC's `setMaxRows` or fetch size), kept other rows than Postgres's
  first ones and read the whole table before the first row. It now returns Postgres's rows, a 100-row preview in
  under a second, and an `unnest` of any expression or a list over two columns does too; the shapes that still differ
  are registered (`limit-lateral-filter`). A count or a `GROUP BY` over such a join keeps the plan that is faster there.
- **`count(DISTINCT id)` of a table's primary key**, a BI tool's count of entities, spilled to disk and took minutes
  on a large table; where the join cannot repeat a row it is computed as the count it equals, in seconds.
- **`EXPLAIN ANALYZE` of a whole-table `count(*)`** reported another statement's plan; `EXPLAIN` of a project switched
  from polling to replication said it was polled; a refusal inside an `EXPLAIN` gave the wrong position. A statement
  stopped at a row count the client set was missing from the request log; it is recorded, with the rows it sent.
- A statement that ended early (a `LIMIT`, a cancelled query, a tool closing its cursor) could leave the run's engine
  waiting for ever, and every later statement with it; a stop under a running statement could abort the process. The
  run now notices an engine that stops answering, tells the waiting statements, and starts again (`mason status` counts
  the restarts); a stop ends the engine only once it has shut down.
- A JSON path's storage estimate could be several times too low, the review of stored paths went stale while a path
  was being filled, and an `add` could stall behind a fill. A copy's progress could read backwards or show 100 % before
  the copy was served. `mason remove` reported success after a run that still held the old tables, and a change to
  the sources file's URL while Mason ran was ignored; both are refused or applied now, by name.

## Also

- The README opens with why Mason exists, the measured comparison with a Postgres read replica (15× to 57× faster at
  p95 on the benchmark's statements, rendered from its fixture) and a diagram, and has the demo running by its 70th
  line; every measurement is in docs/MEASUREMENTS.md.
- docs/SQL-SUPPORT.md opens with "At a glance": of the oracle's 3,086 statements, 95% are answered exactly as Postgres
  answers them, 1% differently by a listed decision and 4% refused by name, against 30% for the engine alone; 993
  pieces of Postgres verified, 47 shapes refused, 15 known differences, 7 limits. A double's last digit may differ
  from Postgres's depending on the two machines (`float-last-digit`).
- CONTRIBUTING.md says where the code is and how to run a checkout's `mason`; `SECURITY.md` and the issue forms say how
  to report a statement that differs from Postgres, one that is slow, or a bug.
- The image is `ghcr.io/embeddable-hq/mason-data`, for amd64 and arm64, published by every release as its version and
  `latest`.
