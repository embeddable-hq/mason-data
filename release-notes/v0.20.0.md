# Mason v0.20.0

**Mason no longer leaves a time limit behind on your database's pooled connections. Behind a pooler in transaction
mode, your application's queries could be cancelled after 10 seconds, for up to an hour. After a fatal error in the
synced data, Mason now exits cleanly, and the cause reaches `mason logs`. A failed sync event now says its code and
where it happened, so you can group failures and report them. Metabase's previews of a join to a table with JSON
fields are faster. A host can show its own icon and who is signed in on the web page.** Every project has something
to do first: its pin moves. A script or an alert that filters sync events by kind must change ("Before you upgrade").

## Before you upgrade

- **Move the pin: `version: 0.20.0` in `mason/mason.yml`.** The 0.20.0 command and image refuse a project pinned to
  0.19.x, and say how to fix it. Before 1.0 they only run a project pinned to their own minor version, at their own
  patch or an older one. Set the pin and start 0.20.0 in the same step.
- **On a hosted replica, upgrade the replica before you deploy a project pinned to 0.20.0.** `mason deploy` refuses a
  pin the replica would not run, before it sends anything, and names both versions. `mason replica upgrade
  <org>/<name>` is one way out, where the service offers it.
- **Two sync event kinds have new names.** `copied` is now `full_sync`, and `copy_failed` is now `full_sync_failed`.
  You see them in these places:
  - `mason logs --events` and its `--json`;
  - `mason status`'s Sync errors section, and `recentErrors` in its `--json`;
  - the Syncs filter on the web page.

  If a script or an alert filters on an old name, change it in the same step. Events recorded before the upgrade keep
  their old names. They still show in the full list, but an old `copy_failed` no longer counts as a failure.

## What changes

- **A failed sync event says its code and where it happened.** `mason logs --events --json` and `/api/events` give
  each failure a `code` and an `origin`.
  - The code is the error's SQLSTATE when your database failed it. It is the system's error when the network or the
    disk failed it (`ECONNREFUSED`, `ENOSPC`). Otherwise it is the error's class (`conversion_error`), or `unknown`.
  - The origin is a file and a line in Mason's code, such as `src/duck/sync.ts:3637`.

  Group failures by the code. Give the origin when you report one. An event that is not a failure has neither. The
  Sync events page shows both under a failure's message.
- **A query that failed inside Mason says where.** A request-log row answered with `XX000` has an `origin` in `mason
  logs --requests --json` and `/api/requests`. Every other row has none.
- Both keys are new. Events and requests recorded before you upgrade are kept, and read with both keys null.
- **Metabase's preview of a join to a table with JSON fields is faster.** This is the preview you see when you join a
  table in Metabase's query builder and show fields it unfolds from a JSON column. Over a 3 M-row table, the 2,000-row
  preview took about 5 s. It now takes about 0.6 s. Postgres still answers it faster, so there is more to do. The
  20-row preview is faster too, when the table you start from is the bigger one. Mason no longer loads every row of
  the other table into memory first. Both previews still return any rows of the join, as Postgres allows for a query
  with no ORDER BY.
- **The SQL support list says plainly how Mason prints a `numeric` column with no precision.** Rails makes one from
  `t.decimal`. Mason prints every value of such a column with the most decimals any of its values has. So `12.5`
  reads `12.50`, and `0` reads `0.00`. The values are right. Only their trailing zeros differ from Postgres's. To get
  the same text from Mason and Postgres, cast the column to `numeric(p, s)` or use `round(x, s)`. A fix is planned.
- **For a host that serves the web page (`mason serve`):**
  - **The page can show your own icon in the browser's tab.** Set `MASON_UI_ICON` to a `data:` URL of a PNG or SVG
    image in base64, up to 4096 bytes. The icon is part of the page, so the browser makes no extra request for it.
  - **The page can show who is signed in.** Set `MASON_UI_ACCOUNT` to JSON with a `label` and a `url`, such as
    `{"label":"ada@example.com","url":"/account"}`. The label shows at the foot of the sidebar, as a link to the URL.
    On a narrow window it is in the menu, with the nav.
  - **A host view's link can be marked as a destructive action.** Give it `"danger": true`, and the page draws it in
    red, like the Remove button on the Tables page. A link that is both `primary` and `danger` is refused, and the
    view says why. So is a `danger` that is not `true` or `false`.

  A value of `MASON_UI_ICON` or `MASON_UI_ACCOUNT` that Mason cannot use stops the start. The message says what is
  wrong and what a valid one looks like. Unset, the page is as before.

## What was wrong and is now right

- **Mason no longer leaves a time limit on your database's pooled connections.** When the web page checked whether a
  table could be kept current by replication, Mason set a 10-second time limit on its connection and never took it off.
  Behind a pooler in transaction mode (PgBouncer, or Supabase's default pooler URL), that connection is handed on to
  your application next. Your application's queries could then be cancelled after 10 seconds, for up to an hour.
  `mason mcp` did the same on Mason's own Postgres API, with each tool call's time limit. Now each limit ends with
  Mason's own query, whatever pooler sits in between.
- **After a fatal error in the synced data, Mason no longer aborts on its way out, and the cause reaches `mason logs`.**
  A checkpoint that fails on a full disk is one such error. Mason then ends the run, so that it can start again.
  Sometimes the run aborted instead, with exit code 134 and `terminate called after throwing an instance of
  'Napi::Error'`. The cause could then be missing from `mason logs`. Now the run waits up to 5 seconds for the synced
  data to close. Then it writes its log to the end and exits with code 1. If the synced data is still closing after 5
  seconds, the log says so, and the run exits anyway.
- **A polled table no longer costs an extra connection to your database now and then.** On some machines, Mason's
  timer for the next poll woke a moment early. Mason then connected to your database, found no table due yet, and
  connected again a moment later to poll it. Now every timer waits until its time has come.
- **A table's columns dialog on the web page names the same choice as its row.** On the Tables page, a table that
  leaves out columns which look like secrets says "All but 7 columns". Its columns dialog said "All columns, … but
  password, …", so it read like a different choice. Now the dialog's choice starts with the same words, "All but 7
  columns", and names the columns left out.

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of every LIMIT with no ORDER BY over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join has
  no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in every release since 0.8.0. It was found by reading the code and has not been reproduced.
- **The web page's errors are not recorded under `MASON_UI_READ_ONLY=1`.** A read-only page cannot send them.
