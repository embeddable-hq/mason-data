# Mason v0.14.0

**Behind a load balancer, a proxy or a DNS name, `mason serve` can print the address clients reach
(`MASON_PG_PUBLIC_URL`). `mason serve`'s web page fits better into a site that embeds it: a read-only page can still
edit its tables (`MASON_UI_READ_ONLY_ALLOW=tables`), and its sidebar can send an item to the site's own page and add
the site's links (`MASON_UI_NAV_<ITEM>_URL`, `MASON_UI_NAV_LINKS`). `mason tables --json` gives the entry `mason add`
would write, and `mason doctor --tables` lists the database's tables with its checks.** Every project has something
to do first: its pin moves.

## Before you upgrade

- **Move the pin: `version: 0.14.0` in `mason/mason.yml`.** A project pinned to 0.13.0 is refused by the 0.14.0 command
  and image, with the way out named: before 1.0 they run a project pinned to their own minor version only, at their own
  patch or an older one. Set the pin and start 0.14.0 in the same step.
- **On a hosted replica, upgrade the replica before you deploy a project pinned to 0.14.0.** `mason deploy` asks the
  replica's Mason version first and refuses a project whose pin the replica would not run, naming both versions and the
  ways out; `mason replica upgrade <org>/<name>` is one of them, where the service offers it.

## New

- **Behind a load balancer, a proxy or a DNS name, the URLs Mason prints can name the address clients reach.**
  `mason serve` with `MASON_PG_PUBLIC_URL=postgres://db.example.com:5433/?sslmode=verify-full` makes `mason status`,
  `mason user add` and `mason user list`, and the web page's Connect panels and "Copy the psql line" print that host,
  port, database (optional: the one Mason answers as when none) and `sslmode` (required), with no note to replace the
  host; `mason status --json` marks it `public: true` under `postgres`. Mason cannot see what sits between a client and
  it, so the `sslmode` is yours to choose: `verify-full` needs a certificate signed for that host wherever TLS ends. A
  user, a password, any other parameter, or an `sslmode` other than `disable`, `require`, `verify-ca` or `verify-full`
  refuses the start, naming the setting and never repeating its value. Unset, nothing changes. `mason start` refuses
  the setting.
- **A read-only web page can still edit its tables.** `mason serve` with `MASON_UI_READ_ONLY=1` and
  `MASON_UI_READ_ONLY_ALLOW=tables` keeps Add, Columns…, Name its key…, Remove and Sync now on the Tables page, and
  still refuses every other change the page sends (users, cancelling a statement, sharing). `MASON_PROJECT_READONLY=1`
  still refuses an Add or a Remove. Any other value, or the setting without `MASON_UI_READ_ONLY=1`, refuses the start.
  `/api/state` and `mason status --json` say what the page still changes as `pageReadOnlyAllow` (`["tables"]`, else
  `[]`). Unset, nothing changes. `mason start` refuses the setting.
- **A web page embedded in another site can send part of its sidebar to that site.** With `MASON_UI_NAV_<ITEM>_URL`
  set (`OVERVIEW`, `TABLES`, `USERS`, `QUERIES`, `USAGE` or `SYNC_EVENTS`), that sidebar item, every link of the page
  into that view and the view's address (`#users`) go to the site's own page instead, in the same tab.
  `MASON_UI_NAV_LINKS`, a JSON list of at most 5 `{"label","url"}`, adds the site's links to the sidebar as a group of
  their own. URLs and labels follow `MASON_UI_BACK_URL`'s and `MASON_UI_BACK_LABEL`'s rules; anything else refuses the
  start, as do a misspelt `MASON_UI_NAV_*` name and an item's URL whose `#fragment` names a view that is replaced (the
  page would go round in a loop). A replaced item is only a link: the server still answers that view's requests, so
  set `MASON_UI_READ_ONLY` too if changes should be made on the site alone. `/api/state` and `mason status --json` say
  them as `pageNav`. Unset, nothing changes. `mason start` refuses these settings.
- **`mason tables --json` gives the entry `mason add` would write.** Each table's `entry`, as the sources file's
  `tables:` map holds it (`{ "orders": { "exclude": ["api_token"] } }`; for a table with no primary key, with the `key:`
  of a unique index over NOT NULL columns when it has one; `null` when `mason add` would refuse it, `reason` saying
  why), and each column's `secret`: whether `mason add` leaves it out as a secret unless named. A tool that writes the
  sources file itself can write what `mason add` would, without copying its rule.
- **`mason doctor --tables` checks the database and lists its tables on one connection.** For a person, the tables a
  line each after the checks; with `--json`, the answer also carries `tables`, as `mason tables --json` gives them. They
  are given whenever the database's catalog was read, though another check failed (the answer still fails), and are
  absent when it was not (no project yet, or the database out of reach). Without the flag, `mason doctor` answers as
  before.

## What was wrong and is now right

- **`mason tables` no longer lists as addable a table `mason add` would refuse.** A table hidden from the user by
  row-level security, for one, was listed as addable (`addable: true` in `--json`), and `mason add` then refused it.
  It is now listed with `mason add`'s refusal as its reason; a table with no primary key whose `--key` would still be
  refused says both.
- **`mason doctor` says a database whose catalog the user cannot read as the database's failing line**, with the
  database's error (a revoked grant, a server shutting down), where the command stopped on that error alone and said
  none of its checks.

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of an unordered LIMIT over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join that can multiply rows, or over
  an aggregated side, has no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY
  where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in 0.8.0 to 0.13.0. It was found by reading the code and has not been reproduced.
