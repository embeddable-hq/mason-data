# Mason v0.8.0

**How each table stays current now lives in the sources file, per table, and tables stop being kept current on the
upgrade unless that file says otherwise. Roles decide which tables, columns and rows each user reads, and `mason share`
gives a cloud BI tool a temporary address to try Mason from.** Every project and every `mason serve` deployment has
something to do first: its pin moves, its tables need a `sync:` line to stay current, and a tool that connects with the
project's name as its database must change.

## Before you upgrade

Everything here is one change, shipped with the upgrade: 0.7.0 refuses a sources file with `sync:`, `publication:` or
`database:` in it, and a project pinned to 0.8.0. Make the edits, set the pin, and start 0.8.0 in the same step.

- **Write `sync:` in your sources file, or your tables stop being kept current.** With no `sync:` anywhere, every table
  is `off`: it keeps what it holds and is read again only by `mason sync <table>`. That is every file `mason init` wrote
  before this release, and on 0.7.0 those tables were polled every 5 seconds. A project that polled still starts, on `mason start`
  and `mason serve`, and says how many tables are no longer polled, so a dashboard goes stale with no failure. At the top of
  `mason/sources/<name>.yml` for every table, or on one table's entry:

  ```yaml
  sync: poll 5s             # what 0.7.0 did by default; any interval from 1s to 24h
  tables:
    orders: { sync: replication }   # this one from the change log
    events: { sync: off }           # this one only at mason sync events
  ```

  **`sync: poll 5s` at the top polls more than 0.7.0 did.** 0.7.0 left a table over 1,000,000 rows out of its polls; now
  a table is polled whenever its `sync:` says so, and each poll scans the whole table on your database. Give a big table
  `sync: off` or a long interval on its own entry; `mason tables` shows each table's rows, an estimate, so you can find
  those over 1,000,000. The next poll of a table still waits at least four times what the last one took. A changed
  `sync:` keeps the synced data and catches the table up by one poll, never a new first sync.
- **`--replication`, `--poll`, `--publication`, `MASON_CHANGES` and `MASON_POLL_MS` are gone.** Nothing but the sources
  file chooses how a table is kept current.

  | Was | Now write | If it is still set |
  |---|---|---|
  | `mason start --replication` | `sync: replication` | exit 2, nothing starts, the line to write is printed |
  | `mason start --poll` | `sync: poll 5m` (any interval) | exit 2, the same |
  | `mason start --publication <name>` | `publication: <name>`, or `publication: ${PG_PUBLICATION}` | exit 2, the same |
  | `MASON_CHANGES=replication` | `sync: replication` | `mason start` and `mason serve` refuse to start, exit 1, naming the line |
  | `MASON_CHANGES=poll` | `sync: poll 5m` (any interval) | the same |
  | `MASON_POLL_MS=30000` | `sync: poll 30s` | `mason start` and `mason serve` refuse to start, naming the line |

  Check scripts, Makefiles, Compose `.env` files, Helm values and platform variables. `PG_PUBLICATION` stays.
- **A project that replicates must say so in its sources file, or its start is refused.** On 0.7.0 a project stayed in
  replication mode with no flag. Now a project that replicates under a file with no `sync:` at its top or on any entry
  is refused: nothing is dropped or changed, and the refusal names the ways out. That holds for any start, `mason start`
  and `mason serve` alike, and for a `mason serve` volume with no sources file. `sync: replication` keeps the same slot
  and publication, and no table is read whole again. `sync: off` or `sync: poll <interval>` confirms the drop: the start
  drops the project's slot and Mason's own publication, verified gone, and says so. A dropped slot has a cost: writing
  `sync: replication` later makes a new one and catches each table up by one poll, a full scan of each table on your
  database. A file edited to no `sync:` while the run is up keeps the tables it had, and `mason status` says so once
  `mason add` or `mason remove` reads the file again. Mason's own publication now carries the replicated tables alone.
  A `key:` table or one with `REPLICA IDENTITY NOTHING` cannot be replicated: under a top-level `sync: replication`, give
  its entry `sync: poll 5m` (any interval) or `sync: off`, or the start refuses it.
- **A project that ever started with `--publication <name>` must write `publication: <name>`.** The name is recorded, and
  a replicating start that neither the file nor `PG_PUBLICATION` gives a publication is refused, naming the line, with
  nothing made on your database. Taking `publication:` out no longer moves a project to Mason's own: where a publication
  is recorded, that is refused. To move on purpose, write `publication: null`, the literal word; beside a set
  `PG_PUBLICATION` that is refused too. A bare `publication:` with no value is a mistake in the file.
- **A tool's database name is now `mason`, or what the sources file says.** It was the project's name (`mason init
  --name`, the folder, or `MASON_NAME` on a server). A deployment that never set `MASON_NAME` already answers to `mason`.
  Any other tool that still connects with the old name is refused with `3D000`, whose hint names the right one. Saved
  URLs count, a `mason mcp` entry's `MASON_URL` included. Either change the tool's database name, or keep it:

  ```yaml
  database: <the name your tools use>   # at the top of mason/sources/<name>.yml
  ```

  On a server whose sources file has no such line, set `MASON_PG_DATABASE`; `mason serve` refuses the two when they
  disagree, and `mason start` refuses `MASON_PG_DATABASE` and names the line to write instead. `MASON_NAME` still names
  the project and its replication slot, and renaming it over the same synced data is still refused.
- **`MASON_REQUEST_LOG_DAYS` is now `MASON_HISTORY_DAYS`.** Set under its old name, it refuses `mason start` and `mason
  serve`, naming the line to write. It takes a whole number of days, 1 or more, default 7 as before, and now covers
  everything Mason keeps over time in its file: the request log, the sync's events, the usage samples and the synced
  tables' sizes. A long retention costs more disk than it did.
- **Move the pin: `version: 0.8.0` in `mason/mason.yml`.** A project pinned to 0.7.0 is refused by the 0.8.0 command and
  image, with the way out named. On `mason serve` that refusal now comes before anything is written.
- **Roles change nothing until you add a file.** A project with no `mason/roles.yml` runs as it did: every user reads
  every synced table, and `mason start` says so. `mason init` now writes that file, for a new project or one with no
  roles file, with `default: everything` and `tables: all`, which is that same access written down. Keep a `default:`
  in the file: under a roles file with no `default:`, a user added without `--role` reads nothing (`42501` on every
  synced table, with the two ways out in the HINT). `mason start` and `mason user list` name such users.
- **A script reading Mason's output has new keys and words.** These moved with no fallback:
  - `mason status --json` loses `tables[].unsynced` and `engine.pollSeconds`. In `mason status --json` and `mason wait
    --json`, a polled table's `kept` is `{ by: "poll", sync, syncedAt, nextAt, pending? }`: `polledAt` is now `syncedAt`.
  - `EXPLAIN (FORMAT JSON)` names no engine in its keys: `Mason.Copies` is `Mason.Tables`, `Last Poll` is `Sync`, `Last
    Synced` and `Next Poll`, each key that said `DuckDB` says `Engine` (`Sent To Engine`, `Engine Thread Time`,
    `Engine Planning`, a multi-root plan's `Engine Plans`), and `Answered By` is `the engine`.
  - What Mason prints says sync, not copy: `synced orders: …` in the log where it said `copied orders: …`, `Synced
    data` in `mason status`, `Ready: every added table is synced and served.` `--json` keys and values are unchanged
    by this, `copiedAt`, the phase `copying` and `MASON_COPY_PARALLEL` included.
- **Going back to 0.7.0 has not been tried.** 0.7.0 refuses a sources file with `sync:`, `publication:` or `database:`,
  so undo those edits as well as the pin. Mason's own history tables gained columns on 0.8.0, and whether 0.7.0 reads them was not
  tested: keep a way to sync again from scratch (`mason destroy`) before relying on a downgrade.

## New: roles

`mason/roles.yml` says what each user may read: tables, columns and rows. It ships with your `mason/` folder, and an
edit takes effect at the next statement, with no restart.

```yaml
default: everything                 # the role of a user added without --role
roles:
  everything:
    tables: all                     # every synced table and column, later ones too
  analyst:
    tables:
      orders: { columns: [id, status, amount] }
      customers: { exclude: [email] }
  tenant:
    attributes: [tenant]            # a value each user carries
    tables:
      customers: { where: "tenant_id = :tenant" }
      orders: { exclude: [notes], where: "tenant_id = :tenant" }
      order_items: { through: orders }   # the rows whose order this user can read
```

```bash
mason user add metabase --role analyst
mason user add acme --role tenant --set tenant=42
```

An attribute can be a list (`attributes: { regions: list }`), set by repeating `--set`. Its `where:` is yours to write as
`region = ANY(:regions)`: compared as one value, the file is refused at the key.

- **A read past a role is refused as Postgres refuses it** (`42501`). The filter is applied to the statement Postgres
  analysed, so every read of a filtered table is filtered: views, CTEs, subqueries, either side of a join, a prepared
  statement at every Execute. A statement's own expressions run only on the rows the filter keeps.
- **A user missing a value its role reads is refused, never answered with no rows**: every statement gets `42501`, with
  the attribute in the DETAIL and the exact way out in the HINT. `mason start` and `mason user list` name such users.
- **A mistake in the file is refused at its key, with the fix.** While Mason runs, a file edited into a mistake refuses
  the users held to a role (`57P03`) until it is repaired. It never widens what they read.
- **`EXPLAIN` of a statement over a filtered table shows Mason's lines alone**, with no engine plan and no row estimates.
  `EXPLAIN ANALYZE` of one is refused, and an operator reads the full plan as a user with no row filter.
- **What a role does not hide:** `information_schema` and `mason mcp` list only what the role may read, but `pg_catalog`
  lists every synced table and column, as Postgres's does for a role with no access. An API token reads everything.
- **Stricter than Postgres row security, on purpose:** whole-row forms and `TABLESAMPLE` are refused on a filtered
  table, a user missing an attribute is refused even for `SELECT 1`, and `mason.attr.*` cannot be `SET`.
- **Some statements are refused for a filtered user that Postgres would answer**: `FETCH FIRST … WITH TIES`, and a
  grouping set that relies on a filtered table's primary key. docs/SQL-SUPPORT.md's `roles` entry names what stays apart.
- **Limits per role are not built.** A role caps no rows, statement time or concurrent statements (issue 92).

## New: `mason share`

`mason share` gives a run on your machine a temporary public address, so a BI tool in the cloud can try it. It prints the
host, port, database, user and password to type in, and Ctrl-C ends the share. The socket requires TLS end to end, and
the password is made by the command, printed once and gone when the share ends. Local tools notice nothing.

```bash
mason share                 # the role: the only one in mason/roles.yml, or you are asked
mason share --role sales    # read as that role
mason share --via bore      # another tunnel (cargo install bore-cli); the default needs only ssh
```

- **It is for trying Mason, on data you may send that way.** The certificate is self-signed and the tool does not check
  it (`sslmode=require`), so a malicious tunnel service could sit in the middle of the handshake. To keep a dashboard
  running, use `mason serve` on a host.
- **A share cannot read as a role whose rows need attributes.** Its login carries no values, so `--role` refuses such a
  role and the choices leave it out. With no roles file a share reads every synced table, and says so.
- **What has been run.** The free route was run against the real service, with synthetic data: the login, the plain and
  wrong-password refusals, Ctrl-C, and the end of the time limit. The service closed the tunnel after 60 minutes, and
  the second tunnel had a different host and port. The free host name held the laptop's public IPv6 address.
- **What has not.** `mason share`'s paid route (`MASON_PINGGY_TOKEN`: a kept address, a tunnel reopened by itself) and
  `--via bore` have never been run against the real services, only against a stub. Treat both as untested.

## What changes for you

- **`mason status`, `mason wait`, `EXPLAIN`, `mason mcp` and the web page say each table's sync and when it was last
  synced**, so an old table is never hidden. `mason sync <table>` reads an `off` or polled table now, from cron or at the
  end of a deploy; a replicated table answers where its stream is. `mason add <table> --sync "poll 30s"` writes the line for you, and `mason add` writes
  `sync: off` for a table over 1,000,000 rows under a file that polls, and says so.
- **The web page shows what happened, not only what is.** Overview, Tables, Users, Queries, Usage and Sync events, with
  charts over a time range, filters, and Sync now. It needs no internet access.
- **New commands.** `mason usage` says what Mason did over time. `mason cancel` stops a running statement. `mason user
  disable` and `enable` refuse a user's logins (`28000`) and bring it back with the same password. `mason logs` adds
  `--events` and `--running`, and filters on `--requests`. Each has `--json`.
- **`GET /metrics` for Prometheus** on `mason serve`'s health port (4140), beside `/healthz`: numbers only, never a
  table, user or statement, so it needs no secret. The Kubernetes Service and the Helm chart carry the scrape annotations.
- **Deployment guides** for Fly.io, Kubernetes (manifests and a Helm chart), Railway and ECS, in deploy/.
- **The CLI ships its own extensions.** One npm package per platform, installed with `@mason-data/cli`, so nothing is
  downloaded after `npm install`: 55 to 94 MiB more on disk and 17 to 31 MiB more to download, by platform, most of which
  the first sync used to download anyway. Where no package fits (musl, Windows on arm64, `--omit=optional`) Mason downloads
  them as before, and says why. `mason doctor` has an `extensions` line. The image holds both extensions, so an `inet`
  cast on a server with closed egress works.
- **`mason init` reads `MASON_DATABASE_URL` first, then `DATABASE_URL`**, and names the one it read, so a bare `mason
  init` can aim at another database than your app's. `mason init --database <name>` writes the `database:` line.

## What was wrong and is now right

- **A large JSON read could take the whole server down.** On a healthy machine, a false alarm of the engine's watch, or
  a real deadlock when a statement was cancelled, ended every session with `57P02` and the run with it. The watch now
  fires only on a stuck thread, and a cancel or close no longer waits on it: a cancelled statement holds its own session
  alone, where a close could hold every other session for 18 seconds.
- **Two quick edits of a table's columns could leave a replicated table wrong.** A batch of changes open across two
  syncs of the table could stall it for five minutes, drop changes so its rows fell behind the database, or replay an
  old change over a newer one. Only the changes meant for the table's current sync are applied now.
- **A session's settings are transactional, as Postgres's are.** `SET LOCAL`, a `SET` undone by `ROLLBACK` or a failed
  block, and `RESET` inside a transaction are answered as Postgres answers them, warnings and reported parameters
  included. `current_setting()`, `set_config()`, `RESET ALL`, `DISCARD ALL` and `SHOW ALL` read the session's values;
  beside a table, `current_setting()` used to answer the engine's own. A role-less `set_config` could change another
  session's settings; it no longer reaches them. Savepoints stay refused.
- **A table could be said to have nothing pending, then refuse the poll asked next**, and a table's `syncedAt` could move
  back by a few milliseconds. A table is said current only when a poll of it would run, and has one sync time.
- **The image's refusal of another release line** was told as `mason start` and came after `mason serve` had written its
  config. It is `mason serve`'s own now, also under `--json`, before anything is written.
- **A lost replication slot was said as "rebuilds from scratch"**, which read as hours of re-reading your database.
  Mason makes a new slot and catches each table up by one poll, and the messages now say so.
- On the web page, a request's + could need several clicks while its row was redrawn. It opens on the first, and a
  request's start and end are shown to the millisecond.

## Known

- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over (issue 79). It was found by reading the code and has not been reproduced.
- **A first sync of a table of large out-of-line values can run out of memory on a small machine** (issue 96). A table
  of about 58 KB a row, nearly all of it in TOAST, failed on a 16 GB machine at the defaults, and the other tables went
  on. Mason tries it again after a wait, from the chunks it has committed. The error offers the engine's own remedies,
  which you cannot apply. What you can set: `MASON_COPY_PARALLEL=1` reads one chunk at a time, and `MASON_DUCKDB_MEMORY`
  raises the engine's limit, with the container's limit about twice that. Both are read at the start, and a start tries
  the table again at once. `exclude:` on the table's entry keeps a large column out of the read. The cause has not been
  measured, and neither setting has been tried against this failure.
- **The image still runs Node 24, and CI runs Node 26**, because of V8 aborts seen on 24 (issue 67).
