# Mason v0.10.0

**A Mason user can now be limited to the addresses it connects from, a hosted replica can be deleted and its page
opened from the command line (`mason replica delete`, `mason ui --replica`), and every command reads the same way: one
form of duration, list flags as a comma list or repeated, `mason -C <folder>`, and each command's spec as data
(`--help --json`).** Every project has something to do first: its pin moves. A few command lines that worked in 0.9.0
now refuse or behave otherwise, each listed below.

## Before you upgrade

- **Move the pin: `version: 0.10.0` in `mason/mason.yml`.** A project pinned to 0.9.0 is refused by the 0.10.0 command
  and image, with the way out named. Make the edits below, set the pin, and start 0.10.0 in the same step.
- **`mason start --port <n>` is now `mason start --ui-port <n>`**: it was always the web page's and the commands' port
  (`MASON_UI_PORT` on a server), never the Postgres API's. The old flag starts nothing: it answers with the line to run
  and exit 2.
- **`mason status`, `mason stop` and `mason logs` refuse an argument** (exit 2): `mason stop myproject` stopped the
  project of the folder it ran in, whatever it named. Run them in the project's folder, or with `mason -C <folder>`.
- **`mason ui` opens a browser only when its output is a terminal**, as `mason login` does; in a pipe or a coding
  agent's shell it prints the address alone, as `--no-open` does. With `MASON_REPLICA` set in the environment, `mason
  ui` now opens that hosted replica's page (said on stderr) rather than the local run's, unless `--ssh` or `--bridge`
  names the target; a `MASON_REPLICA` that is set but empty or not `<org>/<name>` is refused (exit 1), so unset it for
  the local page.
- **`mason deploy` to a replica still being created now waits, up to `--timeout`, and exits 0 or 124**, where it failed
  at once (exit 1). A CI job with a tight time limit should set `--timeout`. "What changes" says what it waits on.
- **A script that reads the exit code of `mason share` or `mason ui --ssh` sees 124, not 1, when the tunnel gives no
  address or the server does not answer within `--timeout`**, as `mason wait`, `mason deploy`, `mason replica create`
  and `mason login` already exit when they run out of time. Every other failure of both still exits 1.
- **`mason replica create` no longer reads the database's URL from `.env`, `.env.local` or the shell, and refuses one
  on its command line.** On a terminal it asks for the URL and reads it without showing it; otherwise it reads it from
  stdin. A script that relied on `DATABASE_URL` being set pipes it instead: `printf '%s\n' "$DATABASE_URL" | mason
  replica create acme/shop --region <region> --size 50`, or `... < url.txt`, or from your secret store's command. With
  nothing on stdin it now stops, sending nothing. A URL given as an argument or a flag to any `mason replica` command is
  refused (exit 2), never repeated, with the line to run instead: a command line is kept in shell history and shown to
  every process on the machine, so if it held a real password, change it. The sources file still names the variable
  (`url: ${DATABASE_URL}`): the replica reads the URL by that name, and it must be `DATABASE_URL`, the one a replica
  sets; a sources file naming another is refused before the URL is asked for. The URL must carry a password and a
  database name, take no query parameter but `sslmode`, name one host, and use a port of 1024 or above; each is refused
  before anything is sent.
- **A sources file that names one of Mason's own settings (`${MASON_…}`) in `publication:` or `url:` is refused when it
  is read**, with the way out; `url: ${MASON_DATABASE_URL}`, which `mason init` writes, still works. See "What was
  wrong and is now right".

## New

- **A Mason user can be limited to the addresses it connects from**: `mason user add looker --from 203.0.113.0/24
  --from 2001:db8:7::/48`, `mason user from looker 198.51.100.0/24` to replace the list, `mason user from looker --any`
  to remove it; `mason user list` shows each user's list (`from` in `--json`, `null` for any address), and `mason user
  … --replica` carries it. A connection from any other address is refused before its password is checked, as Postgres
  refuses one no `pg_hba.conf` line takes (`28000`, `no entry for host "…", user "…"`), and a session held when the list
  changes ends at its next statement if its address is outside it. Behind a TCP proxy the address is the client its
  PROXY header carries (`MASON_PG_PROXY_FROM`). Users without a list connect as before, and `.mason/users.json` files
  written before are read unchanged.
- **`mason -C <folder> <command>`** runs any command as if started in that folder, as `git -C` and `make -C` do; a
  folder that is missing or cannot be read is a wrong command line (exit 2).
- **`mason replica delete <org>/<name>` deletes a hosted replica, and says what it did to your database.** At a
  terminal it asks you to type the replica's name back (elsewhere it needs `--yes`); an owner deletes one, signed in
  within the last 15 minutes. It waits until the deletion is finished (`--timeout`, exit 124 past it), then says, for
  each database, whether Mason's replication slot was dropped and verified gone. When one was not, the service keeps
  the replica (a slot left behind holds its WAL) and the command stops waiting at once: it prints why and the exact
  statement to run on that database, and exits 1; run it, as a user that may drop a replication slot, then confirm on
  the replica's page in the service's web app, and the deletion finishes. `mason replica status` shows a deletion in
  progress the same way, and a replica deleted from the web app as being deleted.
- **`mason ui --replica <org>/<name>` opens a hosted replica's web page in your browser**, for the organisation's owner:
  the service answers an address that opens the page once, for a few minutes, and the CLI opens it (`--no-open` prints
  it instead, `--json` gives `{ url, replica, expiresAt }`). The page is read-only: a replica's users are still changed
  with `mason user … --replica`. Another login, or a CI token, is refused with the service's words; a replica not ready
  yet is said with when to try again.
- **`mason destroy --dry-run` and `mason remove --dry-run` say what would go and change nothing**: destroy lists Mason
  stopped, the replication slot and Mason's own publication on your database (named from what Mason recorded: the dry
  run never connects to the database) and the synced data and state; remove lists the sources file's entries. Both
  prompt for nothing, and `--json` answers with `dryRun: true`.
- **`mason init -` reads the database's URL from stdin**, so its password stays off the command line (`ps`, your
  shell's history). A URL with a password given as the argument to `mason init`, or to `mason mcp --url`, still works,
  with a warning on stderr naming the safer way.
- **`mason wait orders customers` waits for those synced tables alone** (until each one's first sync is done); a
  generated table is still waited for by its name alone. **`mason sync --all`** syncs every table the sources file names.
- **Every command's spec as data**: `mason <command> --help --json` (or `mason help <command> --json`) is
  `{ command, next }`, the command's options with their types, defaults and short names, its forms and positionals,
  its `--json` keys and its exit codes, read from the same description `--help` prints; `mason help --json` is every
  command's, with the guides and the failure codes. `mason version --json` is `{ version, next }`. `mason help agent`
  documents the shape.

## What changes

- **Every `--timeout`, and `mason usage --step`, takes one form of duration**: a bare number is seconds, as before for
  `wait`, `share` and `ui --ssh`, and `30s`, `10m`, `1h` or `1d` (`5 minutes`, `2 days` too). So `mason wait --timeout
  10m` and `mason deploy --timeout 600` now work; nothing that worked before stops working. `--since` and `--until`
  take the same units as an age (`2 hours` too) and still refuse a bare number, which as a time could be a timestamp. A
  `sync:` interval and a `target_lag:` take `d` (`poll 1d`); a bare number in the sources file is still refused, now
  with the line to write (`poll 30s`).
- **Every list flag takes a comma list or the flag repeated, meaning the same**: `mason add orders --columns id
  --columns status` is `--columns id,status`, and so for `--include`, `--key`, `mason logs --outcome`, `mason user add
  --from` and `mason token create --scope` (`--scope deploy,users`). `mason user add --set` stays one value a flag: a
  value may hold a comma.
- **The commands that name a hosted replica all take it the same ways**: `mason replica create` and `status` take
  `--replica <org>/<name>` or `MASON_REPLICA` as well as the argument, and `mason replica list` and `mason token list`
  take `--org` as well as the argument. When `MASON_REPLICA` chose the replica, every such command says so on stderr
  (`using MASON_REPLICA=acme/shop`), and `mason user … --replica` names the replica in its headline and in a `replica`
  key of its `--json` answer.
- **`mason replica create` prints the replica's page**, where its allowlist (the addresses that may query it) is set,
  and `--json` gives it as `replica.page` (`null` when the service names none); `mason replica status` prints it too.
- **What `mason deploy` waits on** (see "Before you upgrade"): when the service answers that the replica is being
  checked or created, that the machine it runs on is not connected just now, or that too many deploys are being sent
  at once, it waits as the service asks and sends the deploy again, saying what it waits on and how long it has waited
  (on stderr; `--json` prints only the answer); past `--timeout` it says no deploy was made. A replica that failed or is being deleted is refused, and the next step is
  `mason replica status <org>/<name>`, no longer `mason login`; a deleted one is answered as a replica that does not
  exist, its next step `mason replica list <org>`.
- **While any user has an address list, a user name that is no user is refused `28000` with the same words as a wrong
  address**, instead of `28P01`, so a connection from outside cannot tell a user with a list from a name that is no
  user. A user without a list still answers a wrong password `28P01`, so its name can be told apart. A project where no
  user has a list answers as before.
- **`mason doctor`'s warnings about a role that may write say what the role has, then one plain recommendation**:
  "Mason only reads, but, for security reasons, we recommend using a role that only reads" (for SECURITY DEFINER
  functions, to review each). They no longer spell out what the role could do. The warning codes, and the statements
  that make such a role, are unchanged.
- **`mason <command> --help` reads in the order you need it**: the usage line, a short description, the examples and
  every flag first; then the longer explanations, and the `--json` answer's shape last (`The --json answer: …`), where
  it once filled the flags in the middle (about 70 lines in `mason status --help`). The text is the same, moved;
  `mason user --help` gains a line for each of its flags.
- **A wrong command line says what is wrong and where its usage is**: a mistyped option is answered with the closest
  one and the command's synopsis (`there is no option --jsn — did you mean --json?`), not with the whole usage, and
  every wrong command line carries a `fix` and a `next` that ends with `mason <command> --help`, where a command's own
  check (`mason wait`, `deploy`, `user`, `token`, …) answered with `next: []`. `mason <command> --help` still prints
  all of it.
- **`not_answering`** (a run that is alive and does not answer, the way out `mason stop`) is now listed among the
  failure codes `mason help agent` names, and a failure never carries a code outside that list.
- **`--json` keys that meant different things in different commands have names of their own beside the old ones**:
  `removedTables` (`mason remove`), `destroyed` (`mason destroy`), `removedUser` (`mason user remove`), `revokedToken`
  (`mason token revoke`) and `loginRevoked` (`mason logout`). The old keys (`removed`, `revoked`) stay until 1.0.

## What was wrong and is now right

- **A sources file can no longer name one of Mason's own settings** (`${MASON_…}`, such as `${MASON_API_KEY}`) in
  `publication:` or `url:`: it is refused when the file is read, with the way out, and the value is never shown. Before,
  `publication: ${MASON_API_KEY}` printed that key in the log as the publication's name and sent it to the source. If
  you run projects written by someone else (CI, a shared server), this closes that path. `url: ${MASON_DATABASE_URL}`,
  which `mason init` writes, still works.
- **`mason usage --since` (and `mason logs --since`/`--until`) with an age too large for a date** (`99999999999d`) crashed
  the command, and the run's HTTP API answered it with a 500. It is now refused as a wrong command line (exit 2), and
  the API answers 400.

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of an unordered LIMIT over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join that can multiply rows, or over
  an aggregated side, has no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY
  where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in 0.8.0 and 0.9.0. It was found by reading the code and has not been reproduced.
