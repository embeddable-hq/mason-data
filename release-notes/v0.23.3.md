# Mason v0.23.3

**A join on a foreign key named in the sources file, a lookup by a random key and many heavy queries at once are
faster.** A project pinned to 0.23.2, 0.23.1 or 0.23.0 runs on 0.23.3 as it is, and no table is read again ("Before
you upgrade"). Its joins get faster once you name its foreign keys, as "Before you upgrade" says.

## Before you upgrade

- **No table is read again.** To see this for your own project, run `npx @mason-data/cli@0.23.3 upgrade --check` in
  the project's folder while Mason 0.23.2 runs. It lists each table the first start reads again, and changes nothing.
- **The pin needs no change.** Before 1.0 the command and the image run a project pinned to their own minor version,
  at their own patch or an older one, so 0.23.3 runs a project pinned `version: 0.23.2`, `0.23.1` or `0.23.0`. Moving
  it to `version: 0.23.3` in `mason/mason.yml` is optional. Once you do, an older 0.23 command or image refuses the
  project, so move it only once everyone and everything that runs the project has 0.23.3. A project `mason init` makes
  on 0.23.3 is pinned 0.23.3.
- **On Mason Cloud, upgrade the replica first, then move the pin.** `mason replica upgrade <org>/<name>` moves the
  replica to 0.23.3. Mason on the replica restarts, and its connections drop. It goes on running your project pinned
  to an older 0.23 as it is.
- **Plan for more disk.** This release keeps more beside the synced data: a sorted list of keys for lookups by key, a
  reference's hidden numbers and the hidden 15-minute numbers ("What changes"). Text compression saves some of it back.
  On the README's cold benchmark of 100 M orders, the synced data was 8.29 GiB on 0.23.2. It is 7.11 GiB with this
  release's text compression alone, and 9.41 GiB with all of it in place.
  - A project synced before gets the list of keys about a minute after the upgrade, in the background, for each table
    whose keys are scattered. That is about 19 bytes a row for a UUID key.
  - The rest comes later: a reference's numbers once you name it (below), and the 15-minute numbers and the text
    compression as each table is synced again whole.
- **To make your joins faster, name your foreign keys in the sources file.** The upgrade writes no `references:`, so
  until you add them a join reads the keys, as before. `mason add` writes them from the foreign keys your database
  declares. After the upgrade, in the project's folder, with the 0.23.3 command:
  1. Run `mason add <table>` again for each table the sources file syncs. Give each the same flags it was added with:
     `--columns`, `--include` and `--key`. Its `sync:` stays as it is, so `--sync` is not needed. Run it with Mason
     stopped on your machine, so that a mistake changes only the file.
     - Repeat the flags, because a bare `mason add <table>` means every column. A table added with `--columns` would
       be widened, and synced again whole.
     - An `exclude:` that Mason wrote for a column that looks like a secret comes back by itself. An `exclude:` you
       wrote yourself has no flag. For such a table, write its `references:` by hand instead (`mason add --help` shows
       the form).
  2. Check that `git diff mason/sources/` shows only `references:` lines. An entry written on one line, such as
     `orders: { columns: [id, customer_id] }`, is also written out one key a line, with the same values. If a
     `columns:`, `exclude:`, `key:` or `sync:` value changed, undo the edit (`git checkout mason/sources/`) and run the
     adds again with the right flags.
  3. No table is synced again. Mason numbers the keys in place, in the background, a part at a time. Until a table is
     numbered, a join on it reads the keys, as before.
  4. Commit the sources file, and deploy it as any change to `mason/` (README "Change a deployed project"). A deployed
     `mason serve` reads the sources file when it starts, so it takes the references when the deploy restarts it.
  - A Mason before 0.23.3 refuses a sources file with `references:`. So deploy them only to a Mason that has 0.23.3.
    Moving the pin to 0.23.3 in the same commit makes an older Mason refuse the project by its version, which says
    plainly what to upgrade.
- **Going back to 0.23.2 works once you take the `references:` lines out of the sources file.** 0.23.2 refuses a file
  with them. It reads no table again, and answers as before. But upgrading to 0.23.3 again can then give wrong answers,
  and a restart does not fix them:
  - Rows that 0.23.2 polled or streamed into a table have no 15-minute number. In a time zone other than UTC, a group
    by month puts them in a group of NULL. A row that 0.23.2's stream updated in place keeps its old number, so it
    groups under its old month.
  - A row whose foreign key 0.23.2's stream changed in place keeps its old reference number. With the references back
    in the sources file, a join can match it to the row it referenced before.
  - A table that 0.23.2 synced again whole or compacted keeps the list of keys 0.23.3 made before. A lookup by key on
    it can return another row.

  So once you are on 0.23.3 again, sync again whole each table that 0.23.2 polled, streamed, synced whole or compacted
  while it ran. Do it on 0.23.3, since 0.23.2 does not know the list of keys. These steps keep the table's entry as it
  was, with its `sync:`, its `exclude:` and its comments:
  1. Commit the sources file.
  2. With Mason running, run `mason remove <table>`.
  3. Wait until `mason logs` shows the table dropped, with its schema: `dropped public.orders's synced data`.
  4. Put the file back with `git checkout mason/sources/`. This also brings back the references other entries held to
     the table.
  5. Run `mason stop`, then `mason start`. Mason reads the sources file as it starts, and syncs the table again whole.
     The table is not served from the remove until that sync ends.

  A deployment that runs the project read-only (`MASON_PROJECT_READONLY=1`) refuses `mason remove`, and says to make
  the change in your project and deploy it. So deploy the sources file without the table, wait until the deployment's
  log shows the table dropped, then deploy the file as it was.

  Or run `mason destroy`, then `mason start`, and every table is synced again whole. The sources file stays as it is,
  and so do the users. `mason destroy` also deletes Mason's logs and the request log, and drops the replication slot.

## What changes

- **Heavy queries take turns, so many at once no longer spill to disk.** A heavy query keeps many rows in memory: a
  join of two large tables, or a group by, distinct or sort that keeps many rows. A few heavy queries run at
  once, and the rest wait their turn. Before, ten clients that each sent a join of 100 M orders to 5 M customers at once
  took 11 minutes. Together the joins did not fit in memory, so Mason wrote 48.7 GB to disk and read most of it back.
  Four at a time took about 40 s.
  - A light query never waits. A lookup by key, a filter, a count and a group by into a few groups are light, however
    many rows they read.
  - By default one heavy query runs for each GiB of `MASON_DUCKDB_MEMORY`, at most one for each CPU and at least one.
    `MASON_HEAVY_QUERIES` sets the number. `mason start` and `mason serve` say it as they start.
  - A query can be cancelled while it waits. Its `statement_timeout` counts the wait. Either ends it with SQLSTATE
    57014, as Postgres does.
  - The request log has a new column, `waited_ms`: how long a heavy query waited for its turn. It is empty for a
    light query. `mason logs --requests --id <request>` shows it.
- **The sources file says how tables join: `references:`.** Each table's entry can list its foreign keys, on the table
  that holds them: `customer_id: customers.id`. A foreign key of several columns is written as in SQL:
  `(tenant_id, customer_id): customers (tenant_id, id)`. Queries use them: a join on one reads less (the next item).
  A project you have gets them from `mason add` ("Before you upgrade").
  - `mason add` writes the foreign keys your database declares between tables the file syncs. When you add the table a
    foreign key points to, it writes that key on the table that holds it. It says each foreign key it left out, and why.
  - `mason remove` takes the references to a removed table out of the other entries, and says so.
  - `mason add`, `mason remove` and the `exclude:` Mason writes for a new secret-looking column now change only the
    lines they must, and keep every comment in the sources file. Before, adding a table again with other columns, or
    giving a sync to a table written as `{ … }`, wrote its entry again and lost its comments.
  - A reference to a table the file doesn't sync, or to a column it doesn't sync, stops `mason start` with the file, the
    key and the way out. `mason tables --json` shows each table's references in its `entry`.
- **A join on a reference reads small numbers in place of its key.** For each reference in the sources file whose key
  is a UUID, a text, several columns, or a sparse integer, Mason gives each key value a number. It stores the number in
  a hidden column of both tables. A query that joins the two tables on the reference's columns joins on the numbers.
  The answers are the same.
  - On a benchmark of 100 M orders and 5 M customers, the orders' key column a join reads went from 1.60 GiB to
    0.31 GiB for a UUID key, and from 1.20 GiB to 0.31 GiB for a text key. On a laptop, a join on a text key went from
    1.42 s to 0.83 s. A join on a UUID key read from disk went from about 1.1 s to 0.85 s. On a slower disk, such as a
    cloud volume, the saving is larger: a query reads up to 1.3 GiB less.
  - The synced data grows. The hidden columns took about 310 MiB for each reference on the 100 M orders, so the synced
    data went from 4.04 GiB to 5.19 GiB with three references. Its first sync took 53 s instead of 41 s.
  - A dense integer key, such as a serial, gets no number. The key is already as small.
  - Naming a reference syncs no table again. Mason numbers the keys of the tables it has synced in place, in the
    background, a part at a time. Until a table is numbered, a join on it reads the keys, as before.
- **Short text columns are stored many times smaller, so a dashboard that groups or filters on them reads less.** When
  Mason syncs a table, it now chooses how to compress each text column from a sample of its values. A column of short
  or repeated values, such as a status, a type, a country code or a name, is stored with a dictionary. Values of 64 bytes
  or more that do not repeat, such as JSON documents, are stored as before. On a benchmark of 100 M orders, a status column of six
  values went from 645 MB to 41 MB. On the README's cold benchmark at that size, a count by status with one client went
  from 4.03 s to 0.45 s, and the synced data went from 8.29 GiB to 7.11 GiB. The answers are the same. This release's
  other additions take space of their own, so that benchmark's synced data is 9.41 GiB in all ("Before you upgrade").
  - The upgrade reads no table again. A table synced before keeps how it is stored until it is synced again whole, or
    until Mason compacts it. Mason compacts a table by itself once much of its space is deleted rows.
  - To apply it to a table now, sync it again whole, with the steps "Before you upgrade" gives for going back to
    0.23.2. They keep the table's entry as it was. The table is not served in between.
  - Generated tables are stored as before.
- **A group by month, week, day or hour of a `timestamptz` column is faster in a time zone other than UTC.** Mason now
  syncs each such column with a small hidden number beside it: the 15 minutes of UTC its value falls in. A query that
  groups by a unit of the column groups by that number first, and works out each group's local month once, not once a
  row. It reads that number and not the time, so a query read from disk reads much less. On 50 M orders in
  `Asia/Kathmandu`, revenue by month went from 456 ms to 60 ms, and from 5.1 s to 0.6 s with ten clients at once. The
  answers are the same, in every zone.
  - In UTC, a query runs as before, since it is already fast there.
  - A table with a time before 1980 or an infinite one still reads the time of those rows.
  - The synced data grows by about 5%, and the first sync takes about 7% longer.
  - The upgrade reads no table again. A table synced before keeps running its queries as before, until it is synced
    again whole.
- **The web page's "Connect an AI agent" is shorter and leads with what to paste.** With `mason serve`'s MCP endpoint
  on, every client uses its address: the box shows it with Copy, one line per client (claude.ai and Claude Desktop,
  ChatGPT, Claude Code, Cursor) saying where it goes, and one line on signing in. The `mason mcp` way is under it, closed.
  "New user added" shows the MCP URL beside the Postgres URL, with the same instructions closed under them.
- **Connects from's hosted-agent choices are now named for the product: "claude.ai" and "ChatGPT on the web"**, under
  "A hosted agent's servers". Before, they read "Claude (Anthropic)" and "ChatGPT (OpenAI)", and a person using Claude
  Code chose the first and was refused. Choosing one now says that Claude Code and Cursor connect from your own
  computer. A user's row reads "from claude.ai's servers (2 ranges)". The ranges are the same.
  `mason status --json`'s `addressPresets` carry the new labels and each one's short `name`.
- **A lookup by a random key reads a few megabytes, not the whole key column.** A synced table has no index. Before,
  `WHERE id = $1` on a table keyed by a random UUID read every value of its key. One order of 100 M took 13 s on the
  README's cold benchmark. Now Mason keeps a sorted list of such a table's keys beside it, and a lookup by key reads
  that list. Measured at 100 M rows, a lookup read 2 MiB of the synced data where it read 1.6 GiB.
  - Mason chooses the tables by how scattered their keys are, not by the key's type. A table whose keys arrive in order
    needs no list. A serial key that heavy updates have scattered gets one.
  - The list costs disk: about 19 bytes a row for a UUID key (1.8 GiB at 100 M rows). It is made after a table's first
    sync, in the background. At 100 M rows that took about 9 s. Lookups read the table as before until it is ready.
    A table synced before gets its list in the background, about a minute after the upgrade.
  - It is sorted again once 1 % of the table's rows were written since. Queries are answered meanwhile.
  - It applies to `WHERE key = …` and `WHERE key IN (…)` on one table, with a key of one column.
- **`mason login` and `mason logout` name the hosted service Mason Cloud** in their help, with its address
  (https://app.masondata.ai) and `MASON_CLOUD_URL` for another service. What they do is unchanged.

## What was wrong and is now right

- **The web page's Users list cut "not used in the last 7 days" short, with no way to read it.** Its Last used column
  is narrower than those words. Now a hover shows them whole, as it does for every other value a list cuts.
- **A first sync could fail with `Duplicate key "source: <table>, first_page: <n>"` after it ran out of memory.** It
  happened when the synced data reported running out of memory as a part of the table was saved, though that part
  was saved. Mason then read that part again and stopped there. The table was not synced at that pass, and was only
  tried again later. Now Mason checks its own record of what was saved, and goes on. No row was lost or doubled.
