# Mason v0.12.0

**A hosted replica can be upgraded from the CLI (`mason replica upgrade`), `mason replica status` shows the Mason it
runs, and `mason deploy` refuses, before it sends, a project the replica would not run. `mason doctor --json` gives
each of its warnings about the user Mason connects as in parts. A refused connection over TLS is now told why.** Every
project has something to do first: its pin moves.

## Before you upgrade

- **Move the pin: `version: 0.12.0` in `mason/mason.yml`.** A project pinned to 0.11.0 is refused by the 0.12.0 command
  and image, with the way out named: before 1.0 they run a project pinned to their own minor version only, at their own
  patch or an older one. Set the pin and start 0.12.0 in the same step.
- **On a hosted replica, upgrade the replica before you deploy a project pinned to 0.12.0.** `mason deploy` now asks the
  replica's Mason version first, and refuses a project whose pin the replica would not run, naming both versions and
  the ways out; `mason replica upgrade <org>/<name>` is one of them, where the service offers it.

## New

- **`mason replica upgrade <org>/<name>` moves a hosted replica to the newest Mason its service offers.** Mason on the
  replica restarts and its connections drop, so at a terminal it asks for the name to be typed back, and elsewhere (and
  with `--json`) it needs `--yes`. An owner of the organisation upgrades one; a CI token upgrades none. It waits for the
  upgrade within `--timeout` (default 15 minutes; exit 124 past it, with nothing stopped). Within the replica's release
  line the newest version then runs; a newer release line is installed beside the one the replica runs, and starts with
  the first deploy of a project pinned to it, so a project written for the line it runs goes on running. It needs a
  hosted service that offers upgrades.
- **`mason replica status` shows the Mason a replica runs**, the newest its service offers and a newer one installed
  (`replica.mason` in `--json`, `null` when absent), where the service says them, and names `mason replica upgrade` as a
  next step while the replica is ready and a newer one is offered.

## What changes

- **`mason deploy` asks the replica's Mason version before it sends.** When the service says it, a project whose
  `mason.yml` pin fits neither the version the replica runs nor a newer one installed is refused here, naming both, with
  the ways out (write the project for the replica's version, or `mason replica upgrade`), and nothing is sent. A project
  with no pin, a service that does not say the version, an answer this version cannot read, or no answer, leaves the
  check to the replica, which refuses such a project itself, as before. A JSON answer (status 200) that carries
  the login's token, in any key or value, is refused, and nothing is sent.
- **`mason doctor`'s warnings about the user Mason connects as end "Mason never writes, but a role that can only read
  is safer"** (the SECURITY DEFINER listing ends with its own recommendation, to review each function). In `--json`
  each warning's parts are apart, so a program can show the facts and the SQL and give its own next step: **`detail` is
  now the facts alone**, and the sentence it ended with is a new key, `why`. Beside `fix`, unchanged, `fixSql` is the
  SQL to run on the primary and `fixThen` the steps after it. A program that read the sentence from `detail` reads
  `why`. On a terminal the lines read as before, but for the new sentence.

## What was wrong and is now right

- **A refused connection over TLS is told why.** Behind a TCP proxy over TLS, a refused connection (a wrong password,
  a protocol error) sometimes saw "connection closed unexpectedly" instead of the refusal, and a client that sent its
  statements and Terminate together sometimes lost the last answers: Mason closed the connection before what it had
  just sent had left. It now closes once that has left, and a client that reads nothing holds the connection five
  seconds at most.
- **A tunnel client is gone before `mason share` says nothing was left open.** When the tunnel gave no address in
  the time given, or Mason stopped under a share, `mason share` sent its client SIGTERM and exited at once, so a
  client that ignored SIGTERM kept running after it. The client is now waited for, and killed if it is still there
  2 seconds later.
- **A first sync whose chunk ran out of memory now goes on with one reader at once.** It promised to, but while the
  chunk that ran out was rolled back, another reader could take a new chunk of full size beside it, at the moment memory
  was shortest; a test saw it in about 1 run in 25. No rows were lost or read twice: the range that ran out was read
  again, by smaller chunks.

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of an unordered LIMIT over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join that can multiply rows, or over
  an aggregated side, has no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY
  where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in 0.8.0 to 0.11.0. It was found by reading the code and has not been reproduced.
