# Mason v0.23.2

**A hosted agent (claude.ai, ChatGPT, a team's agent platform) can query `mason serve` over MCP, at `/mcp` on the
health port. It is off until you set `MASON_MCP_*`.** A project pinned to 0.23.1 or 0.23.0 runs on 0.23.2 as it is, and
no table is read again ("Before you upgrade").

## Before you upgrade

- **No table is read again.** To see this for your own project, run `npx @mason-data/cli@0.23.2 upgrade --check` in
  the project's folder while Mason 0.23.1 runs. It lists each table the first start reads again, and changes nothing.
- **The pin needs no change.** Before 1.0 the command and the image run a project pinned to their own minor version,
  at their own patch or an older one, so 0.23.2 runs a project pinned `version: 0.23.1` or `version: 0.23.0`. Moving it
  to `version: 0.23.2` in `mason/mason.yml` is optional. Once you do, an older 0.23 command or image refuses the
  project, so move it only once everyone and everything that runs the project has 0.23.2. A project `mason init` makes
  on 0.23.2 is pinned 0.23.2.
- **On Mason Cloud, upgrade the replica first, then move the pin.** `mason replica upgrade <org>/<name>` moves the
  replica to 0.23.2. Mason on the replica restarts, and its connections drop. It goes on running your project pinned
  0.23.1 or 0.23.0 as it is. A replica on an older 0.23 runs a project pinned to its own patch or an older one, but not
  one pinned 0.23.2: `mason deploy` refuses that one before it sends anything, names both versions, and gives
  `mason replica upgrade` as a way out where the service offers 0.23.2.
- **The health port's new limits leave a health check and a `/metrics` scrape as they were.** Both send a short `GET`
  with no body, well inside the new limits ("What changes"). An idle connection was already closed after 5 s.
- **Going back to 0.23.1 after giving a user more than 100 address ranges** stops every user from connecting: 0.23.1
  cannot read such a users file, and refuses all users rather than guess. Cut that user back to 100 ranges or fewer
  before you go back.

## What changes

- **A hosted agent can query `mason serve` over MCP.** `/mcp` on the health port (`MASON_HEALTH_PORT`) serves the same
  tools as `mason mcp`. Nothing changes until you set the settings below (docs/POSTGRES-API.md "From a hosted agent: MCP
  over HTTPS").
  - **The settings**:
    - `MASON_MCP_URL`: the address the agent reaches, through your relay.
    - `MASON_MCP_ISSUER` and `MASON_MCP_JWKS_URL`: your OAuth authorization server and its signing keys. Mason issues
      no token and runs no sign-in page.
    - `MASON_MCP_USER_CLAIM` and `MASON_MCP_USER_ID_CLAIM`: the token's claims that name the `mason user` and its id
      (default `mason_user` and `mason_user_id`).
  - **Each request runs as that `mason user`**, looked up every time: its role, row filters and address ranges apply.
    A user removed, disabled, or removed and added again under the same name is refused at its next request.
  - **What your relay must do**:
    - terminate TLS, and set `MASON_MCP_PLAIN=1` to say so. Off loopback, the start is refused without it.
    - append the client's address to `X-Forwarded-For` on every request (nginx:
      `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`).
    - be named in `MASON_MCP_PROXY_FROM` (its own addresses). A user's ranges are then judged on the last
      `X-Forwarded-For` entry. Without it, they are judged on the peer's address.
  - **The Users page offers Claude's and ChatGPT's published ranges** under Connects from ("Claude (Anthropic)",
    "ChatGPT (OpenAI)"), so a user can be held to that agent alone. A user now takes up to 1,000 ranges (100 before).
  - **A person adds the endpoint by pasting only its URL** as a custom connector. They leave any client ID, client
    secret, token or header field empty: they sign in in their browser, at your authorization server.
  - **A desktop app (Claude Code, Cursor, the ChatGPT desktop app) connects from the person's own computer**, never
    from the company's published ranges. Give its user that computer's address, or anywhere.
  - **If your issuer's keys cannot be fetched for more than 5 minutes, every request is 503** until they can. Mason
    fails closed. `mason serve`'s log says why: check that `MASON_MCP_JWKS_URL` is reachable from the replica.
  - **A request from a browser is refused 403** (`origin_not_allowed`) unless `MASON_MCP_ORIGINS` names its `Origin`
    exactly (comma-separated, such as `https://app.example.test`; none by default). Hosted agents and desktop apps send
    no `Origin`, so they need nothing set.
- **The health port now has request limits**, with or without MCP. It takes a request's headers within 10 s and its
  body within 30 s, closes an idle connection after 5 s, and holds at most 1,024 connections. A tool call's own run
  time is not limited by these.

## Known

- **A client's SQL can put a forged line or control characters into `mason serve`'s log and `mason logs`** (issue
  1133). A statement whose error repeats text the client chose is logged as it came, so a line break in it starts a
  line of the client's own text. This was true before this release too, and it will be fixed. Until then, a log line
  is not proof of what happened, and a platform that keeps one entry per line may show a forged one.
