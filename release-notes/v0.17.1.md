# Mason v0.17.1

**Mason now compacts each synced table by itself, so v0.17.0's disk growth and slower reads are bounded, and the
workaround in v0.17.0's notes (`mason remove`, wait, `mason add`) is no longer needed. A fix comes with it: in v0.17.0
and earlier, a table kept current by the stream (`sync: replication`) could be left with rows twice when it was synced
whole and then caught up while more than about 110,000 of its keys changed: its first sync, the remove-and-add that
v0.17.0's notes gave to compact it, a switch to `sync: replication`, or the replication slot made again. A plain
restart with the slot kept is not affected. New duplicates no longer happen, but rows already duplicated stay until the table is synced again whole: if
you replicate a busy table, check it ("What was wrong and is now right" has the query and the way out). And a generated
table over a `citext` or enum column could be refused or given the wrong type.** A project pinned to 0.17.0 runs on
0.17.1 as it is ("Before you upgrade").

## Before you upgrade

- **The pin needs no change.** Before 1.0 the command and the image run a project pinned to their own minor version, at
  their own patch or an older one, so 0.17.1 runs a project pinned `version: 0.17.0`. Moving it to `version: 0.17.1` in
  `mason/mason.yml` is optional; once you do, a 0.17.0 command or image refuses the project, so move it only once
  everyone and everything that runs the project has 0.17.1. A project `mason init` makes on 0.17.1 is pinned 0.17.1.
- **On a hosted replica, upgrade the replica first, then move the pin.** A replica on 0.17.0 runs a project pinned
  0.17.0, but not one pinned 0.17.1: `mason deploy` refuses that one before it sends, naming both versions, with
  `mason replica upgrade <org>/<name>` as a way out where the service offers it. A project pinned 0.17.0 deploys to a
  replica on either version.
- **If you replicate a table that is busy, check it for duplicate rows after upgrading** ("What was wrong and is now
  right"). Nothing on 0.17.1 removes rows already duplicated.
- **Leave room on disk for compaction.** A table is compacted only with room on disk for its rewrite and a margin (a
  quarter of the table, at least 64 MiB); without it the table waits, said on its line in `mason status`.
- **If anything reads `mason status --json`**, each synced table now has `tables[].copy.compaction` ("What changes"),
  and `mason logs --events` has a new event, `compact_failed`.

## What changes

- **Mason compacts a synced table by itself.** It reads each synced table's space a minute after it starts and every 10
  minutes after, and when a table's deleted rows and small blocks make up half of its space (and at least 4 MiB), it
  rewrites that table from the synced data alone, never reading your database.
  - The table is read and served the whole time. While a polled table is compacted, its polls wait and a `mason sync`
    of it is refused; a streamed table's `mason sync` is never refused, and its changes are written to disk beside it, in the synced data, and applied right after (a
    stop or a crash meanwhile catches the table up by one poll at the next start). It takes about as long as reading the
    table: measured, about 2 s for 6 million narrow rows and 5 s for 650,000 rows of 1 KB on a laptop. One table is
    compacted at a time, and never beside a first sync.
  - It works within `MASON_DUCKDB_MEMORY`, a piece at a time; one that runs out of memory fails alone, the table served
    and kept current as it was, and is tried again later.
  - It starts only with room on disk for the rewrite and a margin (a quarter of the table, at least 64 MiB), checked
    again before each piece; without it the table waits, and its line says how much room it needs and how much is free.
    A disk that runs short partway through fails the compaction (a `compact_failed` event), which is tried again later.
  - **A table with a column named `rowid` is never compacted**, and its line says so.
  - `mason status` and the web page say, on a table's line, that its compaction failed and when it is tried again; or
    its share of deleted rows, from 10 % up, and why it is not compacted when it waits; or when it was last compacted.
    `mason status --json` has it under `tables[].copy.compaction` (`deadShare`, `wasteShare`, `checkedAt`, `at`,
    `seconds`, `error`, `retryAt`, `waiting`). A failure is a `compact_failed` event in `mason logs --events`.
  - The file under `.mason/` does not shrink: later writes reuse the space a compaction gives back.

## What was wrong and is now right

- **The synced data no longer grows without bound on a busy server.** Since 0.17.0 a table kept current by the poll or
  the stream kept the space of every row it updated or deleted, and every table written to between two of the synced
  data's checkpoints kept a block of at least 256 KiB, so the disk under `.mason/` grew and reads slowed. With
  compaction ("What changes"), measured: a table whose rows are updated over and over (5 % of them a round) stays within
  about 2.5 times the size and the read time of a just-compacted one, where without it it kept growing, to 5.4 times
  its size and 4.6 times its read time after 60 rounds; a table appended to a little at every checkpoint stays within
  about twice its size. **The workaround in 0.17.0's notes is no longer needed.**

- **A streamed table's catch-up could leave rows twice.** A table kept current by the stream (`sync: replication`) is
  caught up by one poll after it is read whole, and the stream's changes held meanwhile are applied after that poll;
  when they changed more than about 110,000 of its keys, the rows already there for those keys were not deleted before
  they were written again, so the table held them twice (seen: a 2 M-row table left with 935,331 keys twice) and counts
  and sums over it were wrong. A table was exposed when it was caught up so while your database wrote to it heavily:
  - its first sync, or a sync of it again whole — **including the `mason remove` / `mason add` that v0.17.0's notes
    gave to compact a table**;
  - a change of its `sync:` to `replication`;
  - the replication slot made again, also after `max_slot_wal_keep_size` invalidated it;
  - the stream no longer carrying one of its columns;
  - a stop or a crash during any of these, which catches it up at the next start.

  A plain restart with the slot kept is not affected: the stream reads what Mason missed from the slot, in batches too
  small for this. Mason being down matters only when it fell during one of the above. Those changes are now
  applied once each, whatever their number.

  **This does not repair a table already affected.** A duplicated row stays until its key changes again on your
  database (the stream then replaces every row of that key) or the table is synced again whole; a compaction keeps the
  rows as they are, and `mason sync` does not read a streamed table. To check a table, run over Mason's Postgres API,
  with the table's primary key in place of `id`:

  ```sql
  SELECT id, count(*) FROM orders GROUP BY id HAVING count(*) > 1 LIMIT 10;
  ```

  No row means no duplicate. If there are any, sync the table again whole: with Mason running, run `mason remove
  <table>`, wait until `mason logs` shows `dropped <table>'s synced data` (the table named with its schema), then run
  `mason add <table> --sync replication`. The table is not served in between. If you add it back while Mason is
  stopped, or before that line appears, the add cancels the remove and nothing is synced again. If it is the only
  table you replicate, the remove drops the replication slot on your database and the add makes a new one.

- **A generated table over a `citext` or enum column could be given the wrong type, and its statements refused.**
  Mason named such a column's type by the number your database gives the type, read in Mason's own catalog, where the
  same number can be another type: a synced table's row type. The generated table's column was then declared as that
  row type, and a statement Postgres answers, such as `SELECT id, name FROM kinds WHERE name = 'ALICE'`, was refused
  with `0A000 input of anonymous composite types is not implemented`. Whether it happened depended on your database's
  type numbers, so it could appear after any restart. The column is now always declared as your database's type
  (`citext`, the enum's name), and the table is built again at the next start.

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of every LIMIT with no ORDER BY over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join has
  no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in 0.8.0 to 0.17.0. It was found by reading the code and has not been reproduced.
