# Mason v0.13.0

**`mason deploy` shows what a deploy changes on a hosted replica before it sends, and asks before it removes a synced
table. `mason serve --check` says whether the database can serve a project, every problem at once, without changing
anything. The start now refuses a table the user cannot read, where one was synced empty or failed its first sync.
`mason serve`'s web page can link back to the site that links to it.** Every project has something to do first: its
pin moves.

## Before you upgrade

- **Move the pin: `version: 0.13.0` in `mason/mason.yml`.** A project pinned to 0.12.0 is refused by the 0.13.0 command
  and image, with the way out named: before 1.0 they run a project pinned to their own minor version only, at their own
  patch or an older one. Set the pin and start 0.13.0 in the same step.
- **On a hosted replica, upgrade the replica before you deploy a project pinned to 0.13.0.** `mason deploy` asks the
  replica's Mason version first and refuses a project whose pin the replica would not run, naming both versions and the
  ways out; `mason replica upgrade <org>/<name>` is one of them, where the service offers it.
- **Check that the user Mason connects as can read every table the sources file names.** The start (`mason start` and
  `mason serve`) now refuses, by the table's entry, a table it cannot read:
  - **row-level security that hides every row from the user** (it is on for the table and applies to the user: not the
    table's owner unless `FORCE ROW LEVEL SECURITY`, not a superuser or `BYPASSRLS`; and no permissive SELECT policy
    names `PUBLIC` or a role the user has). Such a table was synced empty, without a word. The refusal names the user and gives the way out: the table's
    owner adds a policy for the rows Mason may read (`CREATE POLICY mason_read ON <table> FOR SELECT TO <user> USING
    (…);`), or you remove its entry.
  - **a table in a schema the user lacks `USAGE` on.** Its first sync failed before; it is now refused at the start as
    a table "this user can read" the database does not have. The way out: the database's owner runs `GRANT USAGE ON
    SCHEMA <schema> TO <user>;`, or you remove its entry. `mason serve --check` names this cause in its fix.

  Run `mason serve --check` with the new image against your project first (below) to see every such table at once.
- **A deploy that removes a synced table now asks to confirm it, so a CI pipeline that removes one needs `--yes`.**
  Every `mason deploy` to a hosted replica now first asks the service what the replica runs, and shows what the deploy
  changes. When it removes a table the replica syncs, it asks for the replica's name to be typed back at a terminal;
  without a terminal, and with `--json`, it is refused (code `refused`, exit 1, nothing sent),
  naming each table and its size, unless `--yes` is given. A deploy that only adds or changes tables is not asked
  about.

## New

- **`mason serve --check` says whether the database can serve the project, before anything changes.** It runs the
  start's checks against the project folder and reports every problem at once, each with its fix: a table the database
  lacks or the user cannot read, a column or key, row-level security that hides every row; for `sync: replication` the
  role, `wal_level`, a free slot or WAL sender and the named publication's tables (with the `ALTER PUBLICATION` its
  owner runs); a roles file naming a table or column that is not synced; or the connection's own failure. `--json`
  carries them as `problems`, each with a `code`. Exit 0 when the database can serve the project, 1 when not. It writes
  nothing and never opens the synced data, so it can run beside a running `mason serve`, for example against a new
  project folder (`MASON_PROJECT=<folder> mason serve --check`) before it is put in place; a hosted service may run it
  to refuse a deploy before the new files are written.
- **`mason serve`'s web page can link back to the site that links to it.** Set `MASON_UI_BACK_URL` to a path on the
  page's host (`/something`, from the host's root) or an `https://` or `http://` URL, and the top of its sidebar shows
  "← Back" on every page, opened in the same tab; `MASON_UI_BACK_LABEL` names it (at most 64 characters). Any other
  scheme, a URL with a user or password or a character that is not printable ASCII, or a label set without the URL
  refuses the start. Unset, nothing changes. `mason start` refuses both settings.
- **`mason deploy` shows what it changes on a hosted replica**: the tables it adds (each a first sync) and removes,
  with their sizes where the service says them, the tables whose columns, key or `sync:` change, the generated tables
  and roles it changes, and the pin. It is shown before the deploy is sent, and by `--dry-run` when signed in; `--json`
  carries it as `plan`, and what was confirmed as `confirmed`. A service that does not say what the replica runs leaves
  the plan unknown, said with why, and the deploy goes on as before.
- **A process beside `mason serve` can rely on the table list and on adding and removing tables.** `GET /api/state`
  (its `tables`), `GET /api/tables/<table>/columns`, `POST /api/pick` and `POST /api/remove`, reached over
  `MASON_UI_SOCKET` with the token from `MASON_UI_RUN_FILE`, are now a documented contract: their bodies, answers and
  refusals keep their shape within a release line (docs/WEB-UI.md "An operator's table edits"). `MASON_UI_READ_ONLY=1`
  refuses the page's edits, never a request with the run's token. Their behaviour did not change.

## What changes

- **When a hosted service refuses a deploy for removing tables nobody confirmed (`unconfirmed_removal`), `mason deploy`
  asks and sends it again.** The service may refuse such a deploy itself, whatever sent it. `mason deploy` then says
  the tables the refusal names, with their sizes, confirms them as above (typed back, else `--yes`), and sends the
  deploy once more as a new deploy, removing exactly those. Where the service could not tell which tables go, the
  question says any synced table the deploy removes will be dropped. A service whose refusal does not name the tables
  leaves the way out as before: deploy again, to be shown the plan and asked.

## What was wrong and is now right

- **A generated table's file whose YAML expands too many aliases is refused as that file's mistake**, naming the file,
  as a sources or roles file's is. `mason deploy` stopped on an internal error.
- **A table hidden by row-level security is no longer synced empty without a word**, and a table in a schema the user
  lacks `USAGE` on no longer fails its first sync: both are refused at the start (above).

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of an unordered LIMIT over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join that can multiply rows, or over
  an aggregated side, has no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY
  where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in 0.8.0 to 0.12.0. It was found by reading the code and has not been reproduced.
