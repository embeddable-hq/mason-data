# Mason v0.11.0

**`mason serve`'s web page can now be run for someone else to look at: on a Unix socket (`MASON_UI_SOCKET`), read-only
(`MASON_UI_READ_ONLY=1`), behind a reverse proxy at any path, with its port and the run's token written for a supervisor
on the same machine (`MASON_UI_RUN_FILE`), and `/healthz` saying how it is served. The users page's add form offers a
role, and the image's uid 1000 is now stable.** Every project has something to do first: its pin moves. A proxy in
front of the web page must serve it at an address that ends in `/`.

## Before you upgrade

- **Move the pin: `version: 0.11.0` in `mason/mason.yml`.** A project pinned to 0.10.0 is refused by the 0.11.0 command
  and image, with the way out named. Set the pin and start 0.11.0 in the same step.
- **The web page asks for every file and every answer relative to its own address, and the first visit's redirect (the
  token traded for the cookie) is `./`**, where both were root-absolute (`/app.js`, `/api/…`, a redirect to `/`). So it
  works behind a reverse proxy at any path, such as `https://example.com/tools/mason/`, with no setting, and lands back
  on that address, never the proxy's root. **A proxy must serve it at an address that ends in `/`**: at
  `https://example.com/tools/mason` the page's requests go to `/tools/…`. A proxy that rewrote the page's root-absolute
  paths has none left to rewrite, and a script that followed the trade and expected `Location: /` now reads `./`. The
  run still checks every request for its own Host and every change for its own Origin, so the proxy sends those.
  `mason ui` opens it at `/` as before.

## New

- **`mason serve` can serve the web page on a Unix socket too: set `MASON_UI_SOCKET`** (for example
  `/mason/data/.mason/ui.sock`), so a supervisor or a local reverse proxy on the same machine reaches the page without a
  published port or a `docker exec` per request. The socket is mode 0600 in a folder only Mason's user can write (else
  the start is refused, saying why), a stale one a crash left is replaced, anything else at the path is refused and left
  alone, and it is removed on exit. A request on it passes the same guard as one through `mason ui --ssh`. Unset,
  nothing changes; `mason start` refuses it.
- **`mason serve` can serve a web page that only shows: set `MASON_UI_READ_ONLY=1`.** The page then offers no Add,
  Remove, Sync, Disable, Enable, Cancel, Add a user or Connect from anywhere, and refuses every change it is sent,
  through `mason ui --ssh` or the socket alike, saying the page is read-only here. What it shows is unchanged. **It
  holds only for someone who reaches the page through a tunnel or the socket, never for whoever holds the run's
  token**: a request with the token is the `mason` commands' (`mason add`, `mason sync`, `mason cancel` beside the
  server) and is served as before, so a supervisor never hands a viewer the token, or `MASON_UI_RUN_FILE`'s file.
  `MASON_PROJECT_READONLY=1` is what refuses the commands' edits of the project's files. Anything but `0` or `1` refuses
  the start; `mason start` refuses it.
- **A supervisor on the same machine can find the page's port and the run's token: set `MASON_UI_RUN_FILE`** (for
  example `/mason/data/.mason/run.json`). Once Mason answers, `mason serve` writes `{ "port", "token" }` there, and
  nothing else, to open a tunnel to the page without reading `.mason/config.json`. The token grants the `mason`
  commands' writes as well as a tunnel, so the file is held to the socket's bar: mode 0600, in a folder only Mason's
  user can write (else the start is refused, saying why), written whole, never through a link or over a file that is not
  a stale one of Mason's own, and removed on exit. Unset, nothing changes; `mason start` refuses it.
- **`/healthz` says how the web page is served, while Mason starts too**: `page: { socket, readOnly }` (the socket's
  path or `null`, and whether `MASON_UI_READ_ONLY=1`), so a supervisor can tell a Mason without a socket from one still
  starting. `mason status --json` says `pageSocket` beside `pageReadOnly`. The keys they had are unchanged.
- **The web page's Users form offers a role** where `mason/roles.yml` names roles: the file's `default:` is chosen
  first and marked, and any other role it names can be picked, as `mason user add --role` does. Before, every user
  added from the page got the default role. A role the file no longer names is refused, saying why. With no roles
  file, or one that cannot be read, the form is as before. `--set` attributes are still given with `mason user add`.
- **The image's uid and gid 1000 (`node`) are stable**: a release that changes them names it under "Before you upgrade".
  So a supervisor may create the folder of `MASON_UI_SOCKET` or `MASON_UI_RUN_FILE` owned by `1000:1000`, mode 0700,
  and check that the socket or the file is owned by uid 1000; it reads the 0600 run file as uid 1000 or as root.

## What changes

- **`HEAD` on the web page's and the API's routes answers as `GET` does**, without the body, where it answered 404.

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of an unordered LIMIT over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join that can multiply rows, or over
  an aggregated side, has no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY
  where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in 0.8.0 and 0.9.0. It was found by reading the code and has not been reproduced.
