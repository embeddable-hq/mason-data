# Mason v0.19.0

**Two fixes for tables kept current by replication come first. If the replication slot was dropped while Mason ran,
the stream could stay stopped for the rest of the run, and the tables served old rows with no error. Now the stream
always starts again by itself. A table being compacted is no longer called current while its newest changes wait.
A running Mason no longer connects to your database every 10 seconds while idle, so a serverless database can
suspend. Metabase's cards that group by a JSON field or bin a number are many times faster. The web page's Overview,
Tables, Users and Queries pages are simpler, and every time range is live.** Every project has something to do first:
its pin moves. Scripts that pass `--remote` or read `mason status`'s human output must change ("Before you upgrade").

## Before you upgrade

- **Move the pin: `version: 0.19.0` in `mason/mason.yml`.** The 0.19.0 command and image refuse a project pinned to
  0.18.x, and say how to fix it. Before 1.0 they only run a project pinned to their own minor version, at their own
  patch or an older one. Set the pin and start 0.19.0 in the same step.
- **On a hosted replica, upgrade the replica before you deploy a project pinned to 0.19.0.** `mason deploy` refuses a
  pin the replica would not run, before it sends anything, and names both versions. `mason replica upgrade
  <org>/<name>` is one way out, where the service offers it.
- **Drop `--remote` from your scripts.** `mason init --remote` now fails as an unknown option, with exit 2. A database
  on another machine needs nothing extra now ("What changes"). An older `.mason/config.json`'s `"remote"` key is
  ignored.
- **A script that reads `mason status`'s human output must change.** The rows have new labels:
  - Database is now Source;
  - Source (the sources file) is now Sources file;
  - the Changes row is gone;
  - Disk is now Free disk;
  - Sessions is now Connections open;
  - the Mason row is now two rows, Version and Up;
  - a table's line says "not kept current" in lower case, where it said "NOT kept current".

  A script that searches for the upper-case words must change too. `mason status --json` is unchanged, except for a
  new `users` field. Read `--json` where you can.
- **`mason init --json`: the information lines moved from `warnings` to a new `notes` list.** These are the line about
  a database on another machine, the line about your main database, and the tip about a password in the URL. `mason
  status --json`'s `warnings` no longer has the first two either.
- **Handle the new state `compacting` if you read a replicated table's state from `--json`** (`mason status`, `mason
  wait`). It is a table that is being compacted while its newest changes wait ("What was wrong and is now right").
- **`mason logs --events` says "Mason" where it said "(the sync)"** for an event of no one table. `--json` still has
  `table: null` there. There is a new event kind, `ui_error`, which is a failure, so `--failed` lists it too. The new
  kinds `polled` and `streamed` appear only with the new `--scheduled`.
- **`GET /api/tables/<table>/sync`: `polls[].cost` is now an object, not a sentence.** It is `{ rows, scanSeconds,
  everySeconds, busyPercent, basis, rowsPerSecond }`, or null for a table that is not big. This is the endpoint the web
  page reads. No `mason` command prints it.

## What changes

- **A database on another machine works with no extra step.** `mason init` and `mason start` no longer stop for it.
  They say once: "Your database is on another machine. Mason will sync the tables you choose to this machine."
- **Your main database is information, not a warning.** `mason init`, and `mason start` until the first sync is done,
  say that Mason only reads from it and keeps its load small, and that you can point Mason at a read replica instead.
  `mason status`'s Source line ends with "your main database" or "a read replica".
- **Calmer words.** A password in `mason init`'s URL is now a tip: your shell's history holds it, so next time put
  the URL in `.env`. `mason doctor` no longer warns about CREATE in schema `public` when that is only the default of
  Postgres before 15. A grant someone made is still a warning. The note for a serverless database names everything
  that keeps it awake.
- **Mason records the web page's own errors.** If a bug in the page stops it from working, you see a `ui_error` event
  in `mason logs --events`, on Sync events, and among `mason status`'s recent errors. `/metrics` counts them in the new
  `mason_ui_errors_total`. The event says which page and file hit the error, never the error's message, which could
  quote your data. At most 10 are recorded a minute.
- **Scheduled syncs can be listed.** Run `mason logs --events --scheduled`, or tick Scheduled syncs on the Sync events
  page. Each scheduled poll is a row. A replicated table gets at most one row a minute, only when changes arrived. They
  are kept for `MASON_HISTORY_DAYS`, like every event. At `poll 1s` that is up to 86,400 rows a day for one table.
- **The web page:**
  - **The Overview is shorter.** A "mason status" box at the top says Ready, Under way or Failed, what that means for
    the synced data, and the Source. Getting started has three steps: Mason is running, Sync a table, and Create a
    user. It is done while at least one table is synced and one user exists. If you remove every table or every
    user, it comes back. Until it is done, it is all the Overview shows, under the "mason status" box once a table is
    added.
  - **Two new cards: Errors and Query errors, for the last day.** Each links to its list. They replace the lists of
    recent errors. The table of the last day's and week's queries is gone, and so is the Overview's Connect panel. The Postgres
    URL is on the Users page and in `mason status`.
  - **Tables has two lists, Added and then Not added**, each with its count. The Show filter is now one box, Failed
    only. A table's State says Syncing while you sync it from the page. Its column form offers All columns or Only
    these columns.
  - **A big table's Sync choice says what a scheduled sync costs once**: the rows, how long a scan takes, and for each
    interval how busy it keeps one connection to your database. A share of 10 % or more is shown as a warning.
  - **Users lists the users first, in Active and Removed tabs.** Then comes the box that adds one, then Connect. A new
    user's URL and password open in a dialog that closes only when you click "I have copied it", since the password is
    not shown again. The dialog says when a tool first connects with it. A line under the form says where roles are
    set.
  - **Connect from anywhere is now Temporary cloud login, on the Users page.** It opens what `mason share` opens, for
    a tool in the cloud that cannot reach your machine. It is not offered under `mason serve`.
  - **Every time range on Queries, Usage and Sync events is live**, and updates by itself. Now is renamed Last 15
    mins, and Refresh is gone.
  - **Queries is shorter.** The time range is its only window, and the User filter is a list of your users.
  - **Smaller changes.** Each box that opens beside a button has an X to close it. An empty list is one quiet line.
    Sync events says each kind in words, such as Scheduled sync or Live sync. Connects from is a dropdown again.
- **Faster queries:**
  - **A JSON field whose path your tool sends as a parameter is read as fast as one written in the query.** Metabase
    sends JSON paths this way. A card grouped by a JSON field took 11 to 16 times as long as on Postgres. It now takes
    two to three times Postgres's time.
  - **A chart that bins a number is now faster than on Postgres.** Metabase bins a number column for its X-rays and
    for binned fields. Over millions of rows, such a card took 16 to 25 times as long as on Postgres. Now it takes
    about half Postgres's time. This holds for columns of `numeric(p, s)` and the integer types. The answers are the same as
    before, to the last digit.

## What was wrong and is now right

- **A running Mason no longer connects to your database every 10 seconds while idle.** It read the database's list of
  tables on a timer, whatever each table's sync. So a serverless database (Neon, Aurora Serverless) never suspended,
  and every database logged about 8,600 connections a day. Now Mason reads the list only when you ask:
  - `mason status`, `wait` and `doctor`, and the open web page, reuse a read under a minute old. They never wait more
    than 2 seconds for a new one.
  - `mason tables`, `add` and `remove`, and the page's Columns and Sync choices, read the list as it is now. If they
    cannot (a migration holds a lock, or the connection went silent), they say so and change nothing. A database with
    many tables can take a minute to read, and `mason add` says it is still going.
  - With every table `sync: off`, a run nobody asks opens no connection after its first sync.

  The read is one short read-only transaction, so it leaves no setting behind on a pooled connection. It works behind
  a connection pooler in transaction or session mode (PgBouncer, Supavisor, Neon's proxy). It does not work in
  statement mode, where Mason's first sync already fails.
- **Tables under `sync: replication` no longer stop being kept current after the replication slot is dropped.** The
  stream waited a moment before it started again. Another sync asked for in that moment could cancel the restart. The
  tables then served old rows for the rest of the run, with no error. Now the stream always starts again.
- **A replicated table is no longer called current while Mason compacts it.** During a compaction, its newest changes
  wait until it ends, and queries read the rows as they were. Before, `mason status`, `mason wait` and the web page
  said the table was current. Now its line says it is being compacted and when it was last synced. If the compaction
  takes over two minutes, the table shows as behind until it ends. No data was ever lost.
- **Under `sync: replication`, a table whose sync failed is always tried again.** When two tables' syncs failed at
  different times, the later one could wait until Mason started again. Now each is tried at its own time.
- **A table whose sync failed is tried again with one pass, not two.** On some machines, Mason woke a millisecond
  early, skipped the table, and ran a second pass that checked your database for nothing.
- **On a phone, a user's row on the Users page can be pressed.** Its buttons covered the user's role and where it
  connects from.
- **The time range on Queries, Usage and Sync events no longer moves when you choose a range.**

## Known

- **A generated table can't yet hold a numeric that divides (an average is one); is a variance or a standard deviation, which Postgres computes exactly at decimals it picks per value, rounded, cast to numeric(p,s) or not; is a sqrt, exp, ln, log or power, whose decimals Postgres picks per value, rounded, cast to numeric(p,s) or not, whatever the decimals of what it is computed from; is a JSON number's text cast to numeric with no scale (cast to numeric(p,s), it is stored); has more than 18 decimals, at the end or on the way; sums values whose decimals the rows decide; is a CASE, GREATEST, LEAST or COALESCE of values with differing decimals; or is cast from a double; nor a domain or a composite**, and `kind: live` is refused. Each is refused by file and key before anything is built, said as Postgres types the value (a sqrt or an average of a double is a double, so cast to numeric it is a cast from a double), wherever it sits in the column (under an operator, a coalesce, a round, a cast or an aggregate, or in a scalar subquery, a `WITH` query, a subquery in `FROM` or a `UNION`'s arm), with the way out your own SQL with the cast moved and the aggregate kept (`sum(sqrt(x)::double precision)`), or the `WITH` query, subquery or `UNION` the cast belongs in, given whole. Each of these keeps its reason read back from its text (`::text`, `::varchar`, `|| ''`, a jsonb's `->>`, a `WITH` column), cast to numeric(p,s) or not, so a typmod over a variance's text never stores an approximation; only a stored column's or a JSON number's text read as a numeric is said as a text: a JSON number's, a stored double's or any other. A run that fails (a value past 38 digits, `bigint out of range`, `division by zero`) records Postgres's error, SQLSTATE and DETAIL (`numeric field overflow` says the precision and scale it must fit, on every path), and is tried again after its back-off.
- **`mason status` shows generated tables; the web page doesn't yet.**
- **Pages of every LIMIT with no ORDER BY over a join may overlap**: `LIMIT n OFFSET m` with no ORDER BY over a join has
  no stable order, so a tool paging one can see a row twice and miss another. Add an ORDER BY where the pages matter.
- **A replicated table whose re-read never completes can rejoin the stream with no catch-up**, and miss what the stream
  passed over, as in every release since 0.8.0. It was found by reading the code and has not been reproduced.
- **The web page's errors are not recorded under `MASON_UI_READ_ONLY=1`.** A read-only page cannot send them.
